Indexing Service

Text Chunking Workflow

The complete end-to-end path a parsed arXiv paper takes through TextChunker to become overlapping, context-rich, embeddable chunks.

All logic lives in src/services/indexing/text_chunker.py. The output is a list of TextChunk objects, each pairing text with a ChunkMetadata record plus arxiv_id and paper_id (src/schemas/indexing/models.py). The design balances three pressures: chunks big enough to carry meaning, small enough to embed cleanly, and overlapping enough that no idea is lost at a boundary.

The constructor rejects overlap_size >= chunk_size with a ValueError. The effective stride of the sliding window is therefore chunk_size − overlap_size = 500 words. These three numbers are the only knobs; everything downstream derives from them.

02Entry point & strategy choice

chunk_paper(title, abstract, full_text, arxiv_id, paper_id, sections=None)

chunk_paper() is the public entry point and a router. It attempts the structure-aware section-based path first and falls back to plain word-based chunking whenever sections are absent, unparseable, raise an exception, or yield an empty list.

↓  returns empty, or raises, or no sections at all

The section attempt is wrapped in try/except: any failure is logged as a warning and quietly degrades to the word-based path, so a malformed sections payload can never break ingestion.

03Parse sections

_parse_sections(sections) → Dict[str, str]

Sections can arrive in three shapes; all are normalized to a { title: content } dict:

Input shapeHandling
dictUsed as-is.
listEach item's title/heading and content/text keys are read; missing titles become Section N. Non-dict items are stringified.
strParsed as JSON, then treated as a dict or list per above. Invalid JSON logs a warning and returns {}.

An empty result here means the section path produces nothing, triggering the word-based fallback.

04Filter noise

_filter_sections(sections_dict, abstract) → Dict[str, str]

Front-matter and boilerplate are removed so they never become chunks. A section is dropped when…

  • Empty — content is blank after stripping.
  • Metadata title — _is_metadata_section() matches titles like authors, affiliation, email, arxiv, preprint, submitted, or any title shorter than 5 characters.
  • Abstract duplicate — _is_duplicate_abstract() drops it if the abstract contains or is contained by the content, or if >80% of the abstract's words also appear in it (for abstracts over 10 words).
  • Short metadata content — under 20 words and _is_metadata_content() finds two or more markers (@, arxiv:, university, institute, department, gmail.com, edu…).

If filtering leaves nothing, a warning is logged and the section path returns empty — again falling back to word-based.

05Build the header

One header string is built once and prepended to every section chunk:

{title}\n\nAbstract: {abstract}\n\n

This guarantees each chunk carries the paper's identity and gist even when retrieved in isolation, which improves standalone relevance scoring during search.

06Route each section by size

Filtered sections are iterated in order. Each is routed by its word count into one of three branches. A running small_sections buffer carries undersized sections forward until they can be flushed.

< 100 words  —  too small → buffer
Appended to the small_sections buffer. The buffer is flushed via _create_combined_chunk() when this is the last section, or when the next section is ≥ 100 words. See stage 07.
100 – 800 words  —  ideal → one chunk
Becomes exactly one chunk built as header + "Section: {title}" + content via _create_section_chunk(). The common, happy case.
> 800 words  —  too large → split
Handed to _split_large_section(), which windows the content and re-prepends the header to each part. See stage 08.

07Combine & merge small sections

_create_combined_chunk(header, small_sections, existing_chunks, …)

When the buffer flushes, the accumulated small sections are stitched into a single block:

  • Each buffered section is rendered as Section: {title}\n\n{content} and joined together under the header.
  • Merge-back check: if the combined block plus header is still under 200 words and a previous chunk exists, the block is appended onto that previous chunk instead of standing alone — its metadata title gains a + Combined suffix and it returns no new chunk.
  • Otherwise a new combined chunk is emitted. Its title concatenates up to three section titles with +, and any remainder is summarized as + N more.

This two-level strategy keeps embeddings from being dominated by the repeated header on tiny fragments.

08Split large sections

_split_large_section(full_section_text, header, section_title, base_chunk_index, …)
  • The header is stripped off so only the section body is windowed.
  • The body is passed through chunk_text() — the same sliding window used by the fallback (stage 09).
  • The header is re-prepended to every resulting part, and end_char / word_count are adjusted for the added header length.
  • Each part's section_title is labelled {title} (Part n), and chunk_index continues from base_chunk_index.

09Word-based fallback & sliding window

chunk_text(text, arxiv_id, paper_id) → List[TextChunk]

This is both the top-level fallback and the engine behind large-section splitting.

  • Empty or whitespace-only text logs a warning and returns [].
  • Text is tokenized into words with re.findall(r"\S+", text).
  • If there are fewer than min_chunk_size (100) words, the whole text is returned as a single chunk.
  • Otherwise a window of chunk_size (600) words is taken, then the cursor advances by chunk_size − overlap_size = 500 words so the next window re-includes the trailing 100.
  • Approximate start_char/end_char offsets are computed from joined word lengths; the loop ends once all words are consumed.

Known edge case: in the < 100-word branch of chunk_text() (line 114), _reconstruct_text is called with two arguments (words, text) but the method only accepts words. A paper whose text tokenizes to 1–99 words would raise a TypeError on that path.

10Metadata & output

Every TextChunk carries a ChunkMetadata record:

FieldMeaning
chunk_indexPosition of the chunk within the paper
start_char / end_charApproximate character offsets in the source text
word_countWords in the chunk, including any prepended header
overlap_with_previous / overlap_with_nextWords shared with neighbours (0 for standalone section chunks)
section_titleSource section, combined title, or Part n label; None for pure word-based chunks

Why the workflow is shaped this way

Section-first preserves meaning. A paper's own headings are natural semantic boundaries, so a well-sized section maps cleanly to one retrievable unit.

Size routing avoids both failure modes. Tiny fragments are combined (or merged back) so the repeated header can't dominate their embeddings; oversized sections are windowed so no chunk overflows the embedding model's useful context.

Overlap and headers protect recall. The 100-word overlap keeps boundary-straddling ideas retrievable from either side, and the title+abstract header gives every chunk enough standalone context to be scored on its own. The word-based fallback guarantees an answer even when structure is missing or malformed.
