MetadataFetcher — Modular Workflow Documentation

The orchestration layer that ties everything together: the arXiv client (metadata + PDF downloads), the PDF parser (content extraction), and the database (persistence). DAGs and API endpoints call into this module — not into the individual services directly.

Layer 1 — Factory: make_metadata_fetcher(...)

Purpose: Build a MetadataFetcher with production-tuned concurrency defaults.

DefaultValueReasoning
max_concurrent_downloads5I/O-bound — network can absorb several simultaneous requests
max_concurrent_parsing1CPU-bound (Docling + PyTorch) — too many parallel parses thrash CPU/RAM
Key insight: the asymmetric defaults exist because downloads and parsing have different bottlenecks, so they get separate concurrency limits.

Layer 2 — Constructor: __init__(...)

Wires the three dependencies and the two concurrency limits onto the instance:

  • arxiv_client — used for both metadata fetch and PDF download
  • pdf_parser — for content extraction
  • pdf_cache_dir — falls back to arxiv_client.pdf_cache_dir if not supplied
  • max_concurrent_downloads and max_concurrent_parsing — used to construct semaphores per request

No I/O happens in __init__ — everything is lazy until fetch_and_process_papers is called.

Layer 3 — Top-Level Orchestration: fetch_and_process_papers(...)

This is the single public entry point to the entire pipeline. Three sequential steps, each gated by a flag so callers can opt in/out.

Step 1: Fetch metadata
papers = await self.arxiv_client.fetch_papers(
    max_results=..., from_date=..., to_date=...,
    sort_by="submittedDate", sort_order="descending"
)
  • Always runs (no flag).
  • Empty result → log warning + return early with zero stats.
Step 2: PDF processing (optional, process_pdfs=True)
  • Delegates to _process_pdfs_batch
  • Aggregates pdfs_downloaded / pdfs_parsed counts into the results dict
Step 3: Database storage (optional, store_to_db=True)
  • Requires a db_session — if missing, the request is logged as an error but the pipeline doesn't crash
  • Calls _store_papers_to_db with the parsed content dictionary from Step 2

Result aggregation

Returns a stats dict:

{
    "papers_fetched": int,
    "pdfs_downloaded": int,
    "pdfs_parsed": int,
    "papers_stored": int,
    "errors": [str, ...],     # first 5 logged in summary
    "processing_time": float, # in seconds
}

Any uncaught exception is wrapped in PipelineException and re-raised — callers get a single typed error.

Layer 4 — Concurrent Pipeline: _process_pdfs_batch(papers)

This is where the pipeline becomes interesting. Each paper goes through its own download+parse mini-pipeline, all running concurrently with semaphore-controlled parallelism.

The semaphore pattern

download_semaphore = asyncio.Semaphore(max_concurrent_downloads)  # 5
parse_semaphore    = asyncio.Semaphore(max_concurrent_parsing)    # 1 (prod) or 3 (default)

A semaphore is a counter — only N coroutines can hold it at once. Others wait until someone releases it.

Launching all pipelines at once

pipeline_tasks = [
    self._download_and_parse_pipeline(paper, download_semaphore, parse_semaphore)
    for paper in papers
]
pipeline_results = await asyncio.gather(*pipeline_tasks, return_exceptions=True)
Key detail: return_exceptions=True — exceptions become return values instead of crashing gather. One bad paper can't kill the whole batch.

Result classification (per paper)

For each (paper, result) pair:

  • result is an Exception → general pipeline error
  • result is (True, ParsedPaper) → both download + parse succeeded
  • result is (True, None) → download succeeded but parse failed
  • result is (False, None) → download failed

The classifier populates four lists: errors, download_failures, parse_failures, parsed_papers.

Layer 5 — Per-Paper Pipeline: _download_and_parse_pipeline(...)

This is the core of the parallelism trick — overlapping download and parse phases.

async with download_semaphore:        # ← up to 5 in this block at once
    pdf_path = await arxiv_client.download_pdf(paper)
    # releases download_semaphore here

async with parse_semaphore:           # ← up to 1 (prod) in this block at once
    pdf_content = await pdf_parser.parse_pdf(pdf_path)
Why this is fast: the moment download_pdf returns, the download semaphore is released → another paper's download can start. Meanwhile the current paper enters the parse semaphore queue. The two queues drain in parallel.

Visual timeline (5 papers, 5 download / 1 parse slot)

Paper 1: [DDDDDDDD][PPPPPPPP]
Paper 2: [DDDDDDDD]          [PPPPPPPP]
Paper 3: [DDDDDDDD]                   [PPPPPPPP]
Paper 4: [DDDDDDDD]                            [PPPPPPPP]
Paper 5: [DDDDDDDD]                                     [PPPPPPPP]
         └─ all 5 downloading in parallel
                  └─ parses queue up serially (CPU-bound)

Output

Returns a tuple (download_success, parsed_paper):

  • parsed_paper is constructed by wrapping the paper's ArxivMetadata and the parsed PdfContent into a single ParsedPaper
  • If parsing fails, returns (True, None) — the metadata-only path is still viable

Error handling

Wraps any exception in MetadataFetchingException (typed exception layer, just like the arXiv and PDF parser services).

Layer 6 — Serialization: _serialize_parsed_content(parsed_paper)

Converts a Pydantic ParsedPaper into a dict ready for DB insertion.

TransformationWhy
sections → list of {"title", "content"} dictsStrips Pydantic wrapping for JSON storage
references → plain listSame — pure JSON-serializable
parser_used.value (not the Enum)Stores string "docling", not "ParserType.DOCLING"
pdf_processed: TrueMarks the record as having parsed content
pdf_processing_date: now()Audit timestamp

If serialization itself fails (rare), returns a degraded dict with pdf_processed: False and the error in parser_metadata — the paper still gets stored, just without parsed content.

Layer 7 — Persistence: _store_papers_to_db(...)

Writes papers to PostgreSQL via PaperRepository. Four patterns to note:

Pattern 1: Date string normalization

published_date = (
    date_parser.parse(paper.published_date)
    if isinstance(paper.published_date, str)
    else paper.published_date
)

arXiv returns dates as ISO strings; the DB column expects datetime. Uses dateutil.parser (more lenient than datetime.fromisoformat).

Pattern 2: Graceful merge of metadata + parsed content

paper_data = {core_metadata...}
if parsed_paper:
    paper_data.update(self._serialize_parsed_content(parsed_paper))
else:
    paper_data.update({"pdf_processed": False, "parser_metadata": {"note": "..."}})

Papers with and without parsed PDFs both get stored — the schema (PaperCreate) makes parsed content optional, supporting the progressive-enrichment pattern.

Pattern 3: Upsert via repository

stored_paper = paper_repo.upsert(paper_create)
  • Inserts if new, updates if arxiv_id already exists
  • Prevents duplicates on re-runs (idempotent — you can re-fetch the same date range without polluting the DB)

Pattern 4: Single commit + rollback

db_session.commit()        # commit all papers at once
# on error:
db_session.rollback()      # all-or-nothing
stored_count = 0

Atomicity: if the commit fails, the entire batch is rolled back, and stored_count is reset to 0.

Key Design Patterns

  1. ConcurrencyAsymmetric semaphores — downloads (I/O-bound) and parsing (CPU-bound) get separate concurrency limits
  2. PipelineOverlapping pipeline — release the download semaphore as soon as the download completes; don't hold it through parsing
  3. Resiliencereturn_exceptions=True — asyncio.gather doesn't crash on a single failure
  4. GracefulGraceful degradation — failed parse still saves metadata; missing PDF URL still saves what's known
  5. AtomicityAtomic commit — all-or-nothing DB persistence per batch
  6. IdempotentUpsert idempotency — re-running over the same date range is safe
  7. Typed ErrorsTyped exception layer — MetadataFetchingException / PipelineException shield callers from internal errors
  8. StructuredSingle results dict — caller gets a structured summary instead of opaque return values
