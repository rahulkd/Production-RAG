Hybrid Search Workflow

Module: src/services/opensearch/  ·  Client: client.py  ·  Index config: index_config_hybrid.py  ·  Query builder: query_builder.py

What is hybrid search? A single search that combines BM25 keyword matching (good at exact terms, names, acronyms) with dense vector similarity (good at meaning / paraphrase), then fuses the two ranked lists into one final ranking using Reciprocal Rank Fusion (RRF). It runs entirely inside OpenSearch — the app sends one request and gets back one fused, ranked list.

1. Why hybrid?

Each retrieval method has blind spots. Keyword search misses semantic matches (a query for "transformer attention" won't rank a chunk that says "self-attention mechanism" highly if the exact words differ). Pure vector search can drift on rare tokens, exact identifiers, or numbers. Hybrid search runs both and lets each cover the other's weakness.

MethodStrong atWeak atScoring signal
BM25 (lexical) Exact terms, names, acronyms, rare tokens Synonyms, paraphrase, meaning Term frequency · inverse doc frequency (unbounded, ~0–30)
kNN vector (semantic) Meaning, paraphrase, related concepts Exact identifiers, out-of-vocabulary terms Cosine similarity of embeddings (0–1)

The two signals live on completely different scales, so you can't just add them. RRF sidesteps this by fusing on rank position, not raw score — see §5.

2. The index behind it all

Everything is chunk-level. Papers are split into chunks; each chunk is one OpenSearch document that carries both its analyzed text (for BM25) and its embedding vector (for kNN). Defined in index_config_hybrid.py as ARXIV_PAPERS_CHUNKS_MAPPING.

index.knntrueEnables approximate nearest-neighbor search on the index

Because text and vector share one document, a single hybrid query can score the same chunk on both signals without any join.

4. Query-time workflow

The entry point is search_unified(...). It decides the mode, then delegates. Both search_papers() (BM25) and search_chunks_hybrid() are thin wrappers over the same two private methods.

search_unified(query, query_embedding=None, use_hybrid=True, ...) │ ├─ no embedding OR use_hybrid=False │ └─ _search_bm25_only() → lexical only │ └─ embedding present AND use_hybrid=True └─ _search_hybrid_native() → BM25 + kNN fused by RRF pipeline

4a. The BM25 clause (built by QueryBuilder)

With search_chunks=True, QueryBuilder builds a bool query whose text part is a fuzzy, field-boosted multi_match: 

{
  "bool": {
    "must": [{
      "multi_match": {
        "query": "<user query>",
        "fields": ["chunk_text^3", "title^2", "abstract^1"],  // boosts
        "type": "best_fields",
        "operator": "or",
        "fuzziness": "AUTO",
        "prefix_length": 2
      }
    }],
    "filter": [{ "terms": { "categories": [...] } }]   // optional
  }
}

It also attaches highlight config (<mark> fragments on chunk_text, title, abstract) and _source excludes the bulky embedding.

4b. The hybrid query (_search_hybrid_native)

The key step: take the BM25 bool query from above and place it alongside a knn query inside a single hybrid query. OpenSearch runs both sub-queries and the attached search pipeline fuses their result lists. 

search_body = {
  "size": size,
  "query": {
    "hybrid": {
      "queries": [
        bm25_query,                                              // sub-query 1: lexical
        { "knn": { "embedding": { "vector": query_embedding,     // sub-query 2: semantic
                                  "k": size * 2 } } }
      ]
    }
  },
  "_source": {...}, "highlight": {...}
}

# executed WITH the pipeline attached:
client.search(index=..., body=search_body,
              params={"search_pipeline": "hybrid-rrf-pipeline"})
Over-fetch, then trim. Both sub-queries fetch size * 2 candidates so RRF has enough overlap to fuse well, then results are truncated to size. The hybrid query only fuses correctly when the search_pipeline param is present — without it, OpenSearch will not combine the two lists as intended.

5. Fusion: Reciprocal Rank Fusion (RRF)

Defined as HYBRID_RRF_PIPELINE in index_config_hybrid.py (id hybrid-rrf-pipeline), using the score-ranker-processor with technique rrf and rank_constant = 60.

score(doc)  =  Σ lists i   1 / ( k + ranki(doc) )     with   k = 60

For every result list a document appears in, add 1 / (60 + its rank in that list), then sum across lists. Two properties make this work well:

  • Rank-based, not score-based. The incompatible BM25 (~0–30) and cosine (0–1) scales never get compared directly — only positions matter. No normalization or manual weight tuning needed.
  • Consensus wins. A chunk ranked high by both methods beats one ranked #1 by only a single method. The constant k=60 dampens the pull of the very top ranks so a broad agreement outranks a single strong-but-narrow hit.

Worked example

ChunkBM25 rankVector rankRRF scoreFinal
A131/61 + 1/63 = 0.03231
B221/62 + 1/62 = 0.03232
C1—1/61 = 0.01643
D—11/61 = 0.01644

A & B appear in both lists and dominate C & D, each of which is #1 in only one list. That is RRF rewarding cross-method consensus.

Alternative (not used): weighted normalization

index_config_hybrid.py also keeps a commented-out HYBRID_SEARCH_PIPELINE that L2-normalizes scores and combines them with an explicit weighted harmonic mean (e.g. 30% BM25 / 70% vector). RRF is preferred because it "generally provides better results without manual weight tuning" — the trade-off being you give up explicit control over the BM25-vs-vector balance.

6. Result post-processing

After OpenSearch returns fused hits, _search_hybrid_native shapes them for the caller:

  • Drops any hit with _score < min_score (client-side threshold).
  • Copies _score → score and _id → chunk_id onto each chunk.
  • Attaches highlights if present.
  • Recomputes total as the count of surviving hits (post-threshold).
{
  "total": 7,
  "hits": [
    { "chunk_id": "...", "arxiv_id": "2401.12345",
      "chunk_text": "...", "score": 0.032,
      "highlights": { "chunk_text": ["...<mark>attention</mark>..."] } },
    ...
  ]
}
