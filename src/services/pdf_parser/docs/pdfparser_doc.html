PDF Parser — Modular Workflow Documentation

The PDF parser module turns a downloaded PDF file into a structured PdfContent object containing reconstructed sections and raw text. It is built around Docling (an ML-based PDF understanding library) and lives in src/services/pdf_parser/.

Architectural Overview

The module is composed of 3 files forming a clean 3-layer hierarchy, each with a single responsibility:

┌──────────────────────────────────────────────────────────────┐
│ factory.py — Provides a cached singleton (app entry point)   │
│   make_pdf_parser_service() / reset_pdf_parser()             │
└──────────────────────────────────────────────────────────────┘
                            │ instantiates
                            ▼
┌──────────────────────────────────────────────────────────────┐
│ parser.py — Thin facade with high-level orchestration        │
│   PDFParserService.parse_pdf()                               │
└──────────────────────────────────────────────────────────────┘
                            │ delegates to
                            ▼
┌──────────────────────────────────────────────────────────────┐
│ docling.py — Actual implementation                           │
│   DoclingParser._validate_pdf() + _warm_up + parse_pdf()     │
└──────────────────────────────────────────────────────────────┘
Why this layering? The factory caches the heavyweight model, the facade keeps callers parser-agnostic (Docling can be swapped for GROBID later), and the implementation owns the actual Docling logic.

Layer 1 — factory.py (Singleton Factory)

Purpose: Provide a memoized PDF parser instance so the heavyweight Docling/PyTorch models load only once per process.

make_pdf_parser_service() — cached factory

  • Decorated with @lru_cache(maxsize=1) — first call creates the instance, all subsequent calls return the same cached one
  • Reads config from get_settings().pdf_parser (max pages, max file size, OCR flag, table extraction flag)
Why caching matters: Docling loads PyTorch / transformer models. Re-instantiating per request would burn seconds and GB of RAM.

reset_pdf_parser() — cache buster

  • Calls cache_clear() on the lru_cache
  • Used in tests or when configuration changes at runtime

Layer 2 — parser.py (Facade)

Purpose: Provide a stable API surface so callers don't depend on Docling directly. If GROBID (or any other parser) is added later, this is the layer that chooses between parsers.

PDFParserService.__init__(...)

  • Constructs a single DoclingParser with the configured limits
  • All real work is delegated to the parser instance

PDFParserService.parse_pdf(pdf_path) — main entry point

Pipeline:

  1. Existence check — raises PDFValidationError if the file is missing
  2. Delegate to self.docling_parser.parse_pdf(pdf_path)
  3. Normalize errors:
    • PDFValidationError / PDFParsingException → re-raised unchanged
    • Any other exception → wrapped in PDFParsingException
  4. Null check — if Docling returns None without raising, the wrapper raises PDFParsingException
Key role: This layer exists so swapping parsers (Docling → GROBID → Marker) doesn't require changing any caller code.

Layer 3 — docling.py (Implementation)

This is where the actual PDF processing happens. Three logical phases.

Phase A — Setup (__init__ + _warm_up_models)

__init__ configures the Docling pipeline:

PdfPipelineOptions(
    do_table_structure=True,   # enable table extraction
    do_ocr=False,              # OCR is slow, off by default
)
DocumentConverter(format_options={InputFormat.PDF: PdfFormatOption(...)})

It stores limits as instance variables:

  • max_pages (default 20)
  • max_file_size_bytes (converted from MB at init time)
  • _warmed_up flag

_warm_up_models() is a placeholder — flips a boolean to track first use. Useful hook if you want to pre-load models with a dummy doc later.

Phase B — Validation (_validate_pdf)

Four sequential checks, each raising PDFValidationError on failure:

CheckWhat it doesWhy it matters
Empty filestat().st_size == 0Guards against zero-byte downloads
Size limitFile size ≤ max_file_size_bytesPrevents memory blowup on huge papers
Magic bytesFirst 8 bytes start with %PDF-Detects renamed / corrupted files cheaply
Page countlen(pypdfium2.PdfDocument(...)) ≤ max_pagesPrevents slow processing on 100-page tomes

The page count uses pypdfium2 (a lightweight C-binding wrapper around PDFium) — much faster than letting Docling load the whole document just to count pages.

Phase C — Parsing (parse_pdf)

The actual conversion pipeline:

1. _validate_pdf(pdf_path)         ← gate
2. _warm_up_models()                ← lazy first-call hook
3. converter.convert(...)           ← Docling does the heavy lifting
4. Iterate doc.texts:               ← assemble sections
     - If label is "title" or "section_header" → start new section
     - Else → append text to current section's content
5. Build PdfContent(...)            ← Pydantic output

Section assembly trick: Docling returns a flat stream of text elements with labels. The code walks this stream, using headers as section boundaries to reconstruct hierarchical structure. The current_section dict accumulates text until the next header arrives.

Output shape:

PdfContent(
    sections=[...],          # reconstructed sections
    figures=[],              # intentionally empty (arXiv API has this)
    tables=[],               # intentionally empty
    raw_text=doc.export_to_text(),
    references=[],
    parser_used=ParserType.DOCLING,
    metadata={"source": "docling", "note": "..."},
)
Design choice: Figures, tables, and references are left empty because arXiv's API already provides this metadata more reliably. The PDF parser focuses on what arXiv doesn't give you: structured full-text content.
Phase D — Error Handling

Two distinct error paths:

1. Soft failures → return None (let caller continue):

  • "too large" or "too many pages" → log info, return None

2. Hard failures → raise PDFParsingException:

Detected substringDiagnosis
"not valid"Corrupted PDF
"timeout"Processing timeout
"memory" / "ram"Out of memory
"max_num_pages" / "page"Page-limit related
(anything else)Generic parsing failure

This string-sniffing pattern is fragile but pragmatic — Docling doesn't expose typed errors, so the wrapper inspects messages to give callers actionable diagnostics.

Key Design Patterns

  1. SingletonSingleton via lru_cache — heavyweight model loaded once per process
  2. FacadeFacade pattern — PDFParserService shields callers from Docling
  3. LazyLazy warm-up — _warmed_up flag tracks first use
  4. Fast pre-checkCheap pre-validation — pypdfium2 for page counts (avoids loading full doc into Docling)
  5. Soft vs hardSoft vs hard failures — size / page-limit issues return None; corruption raises
  6. SeparationSingle source of truth for content — figures / tables left to arXiv API; PDF parser owns structured text only
  7. DiagnosisError message sniffing — inspects error strings to surface meaningful exception types
